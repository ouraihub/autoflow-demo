# #13 从新新建分支开发，不要管之前的

## 需求

为通过 GitHub Actions 提交需求并开展开发的仓库协作者，后续处理本 issue 时从新建的独立分支开始，不依赖或沿用之前的分支状态。成功标准：开发工作有新分支作为起点，既有分支及其内容不被本 issue 的工作主动修改；具体分支从何处创建、如何命名及由谁创建，原文没有说明，暂按待确认项处理。
## 现状

- `AGENTS.md`：要求每个导出函数有同目录 `*.test.ts`，并要求 `npm test` 通过；没有分支创建或 GitHub Actions 分支策略说明。
- `README.md`：说明仓库是 AutoFlow 验收项目，示例直接引用 `src/farewell.ts`；没有开发分支约定。
- `package.json`：仅定义 `npm test`，测试命令为 `node --test "src/**/*.test.ts"`；没有分支脚本、发布脚本或分支名配置。
- `src/greet.ts`、`src/farewell.ts`：分别导出 `greet`、`farewell` 字符串函数；现有代码与 issue-13 的分支要求没有直接接口关系。
- `docs/issue-7.md`：记录过一次函数新增的设计和实施过程，未规定分支来源或“忽略之前工作”的处理方式。

当前工作树在分析开始时干净。仓库中未见可依据的分支命名规则、基线分支名称、自动创建分支的脚本或需要迁移的调用方；本次只建设计文档，不修改源码、测试、配置或 `.github/`。
## 方案

1. 本 issue 的设计文档只规定后续开发操作，不新增分支脚本、业务函数或 workflow。当前仓库未见分支策略实现，且用户明确本次只要求分析和规划；将需求落实为“开始后续实现前，基于仓库既有默认基线创建一个新的 issue 专属分支，并仅在该分支开展改动”。
2. 创建前检查工作树及将采用的基线。若工作树存在未提交内容，或先前工作的提交是否需要保留不明确，先停止并记录，不用重置、清理或覆盖的方式实现“不要管之前的”；这避免误删他人数据。只在确认基线后创建新分支。分支名暂建议 `issue-13-new-branch`，待确认仓库命名约定后采用。
3. 不改 `src/greet.ts`、`src/farewell.ts`、测试或 `package.json`：本需求涉及开发流程，不涉及这些函数行为。也不修改 `.github/`；后续若决定需要自动化，再单独明确 workflow 的触发条件与权限，并在获准范围内设计。
4. 其他做法：不直接在当前分支提交，因为这不满足独立新分支的要求；不创建新的 GitHub Actions 自动分支 workflow，因为仓库现有证据不足以确定触发方式、基线和权限，自动化还会扩大变更范围；不丢弃既有工作，因为“不要管之前的”不等于授权删除或重置。
## 影响与风险

- 影响模块：仅约定后续开发的 Git 分支操作；目前没有相关代码模块或函数需要修改。本次唯一文件是 `docs/issue-13.md`。
- 接口与数据：不改变程序 API、运行时行为、持久化数据或依赖。Git 提交基线和分支名尚未由仓库约定，执行者需在后续实施前确认。
- 兼容性：不改现有分支、提交或默认分支配置；不会自动迁移之前的工作。若新分支基线与预期不符，后续变更可能遗漏既有必要提交，应先核对基线。
- 安全与操作风险：强制清理或重置可能删除未提交或尚未合并的工作；方案要求先检查并在含糊时停止，不执行破坏性操作。未引入新的 workflow 权限或凭据使用。
## 待确认

- 新分支应从哪个基线创建：仓库未写明默认分支名或是否包含先前工作的提交。
- 分支命名规则和创建责任人是什么？`issue-13-new-branch` 只是暂定建议。
- “不要管之前的”是只要求本 issue 不基于旧工作继续，还是明确要求新分支不包含之前的提交？未确认前保留现有工作，不删除、不重置、不擅自排除提交。
- 是否需要由 GitHub Actions 自动创建或切换分支？未确认前只按后续开发者创建分支的流程处理，不改 `.github/`。
